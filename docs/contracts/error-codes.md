# 错误码契约 v1.0

> 三个**互不相同**的错误域，本文件把它们分开定义，禁止互相借用。
> owner：后端负责人 · 审阅：前端负责人、嵌入式负责人

---

## 0. 为什么必须先拆开

同一句「命令失败了」，在三层里是不同的东西：

| 域 | 谁产生 | 载体 | 回答的问题 |
|---|---|---|---|
| **业务错误** | 后端业务代码 | HTTP 返回体的 `code` | 这个**请求**能不能被受理 |
| **设备错误** | STM32 固件 | `0x05` 帧的 `DATA[0]` | 设备为什么**拒绝执行**这条命令 |
| **传输错误** | 后端串口层 | 命令记录的 `transport` 列 | 字节到底**有没有发出去** |

把它们塞进一个枚举，就会出现这种对话：
「为什么失败了？」「code 5。」「5 是设备拒绝还是串口断了？」「不知道。」

**规则：**
- 业务错误**不写**进 `command_log`，因为它发生在命令落库之前。
- 设备错误**必须**带 seq，因此**必须**能回填到 `command_log.error_code`。
- 传输错误**不是**错误码，它是一个独立字段，可与任意业务错误同时出现。

---

## 1. 业务错误码（HTTP 返回体 `code`）

沿用 `backend/app/routers/auth.py` 的既有做法：**HTTP 200 + 非零 code**。
前端 `utils/request.ts` 已经把这当唯一业务错误通道，不要改成真实 HTTP 状态码——
一改，前端会把 4xx 当成「网络异常」，把后端精心写的 message 丢掉。

| code | HTTP | 含义 | 前端行为 | 状态 |
|---:|---:|---|---|---|
| `0` | 200 | 成功 | 正常处理 | 已实现 |
| `40001` | 200 | 用户名或密码错误 | 登录页提示 | 已实现 |
| `40002` | 200 | 参数不合法 | toast 后端 message | 已实现 |
| `40003` | 200 | 缺少 `Idempotency-Key` | **不是用户错误**，属于前端 bug；toast 固定文案 | **待实现** |
| `40100` | 401 | token 缺失 | 跳登录页 | 已实现 |
| `40101` | 401 | token 无效或过期 | 跳登录页 | 已实现 |
| `40400` | 200 | 资源不存在（设备/命令/场景/表情） | toast | 已实现 |
| `40901` | 200 | 冲突：同一 `Idempotency-Key` 对应不同请求体 / 该设备已有场景在跑 | toast「操作重复，请刷新后重试」 | **待实现** |
| `50000` | 500 | 服务内部错误 | toast | 已实现 |
| `50301` | 200 | 设备不在线 | **仅提示，不阻止操作** | 已实现（见 §4） |

> `40003` 与 `40002` 分开，是因为它们的责任方不同：`40002` 可能是用户输入问题，
> `40003` 永远是前端代码漏传。合成一个码，联调时两个人会互相说是对方的 bug。

### 1.1 为什么 `50301` 不阻止操作

设备 offline 的定义是「9 秒没收到上行帧」，它可能是蓝牙抖动、可能只是设备睡着了。
命令仍然入队 —— 如果链路其实活着，命令会成功；如果真断了，600 ms 后落 `unknown`。
**提前拒绝反而丢掉了一次本来能成功的执行。**

## 2. 设备错误码（`0x05` 帧的 `DATA[0]`）

`0x05` 帧结构：`LEN=2, DATA=[error_code, seq]`。收到后对应 `seq` 的命令置 `rejected`。

**证据状态必须分清**，不要把提案当实现：

| 值 | 含义 | 证据 | 状态 |
|---:|---|---|---|
| `0x00` | 保留（不得使用） | — | 保留 |
| `0x01` | 校验和错误 | 固件计划「补 0x05 上报：校验错、未知命令、参数越界」（fw.txt:361）按此顺序推断 | **推断** |
| `0x02` | 未知命令码 | fw.txt:362「发一个不存在的命令码，回 0x05 且错误码是 0x02」 | **已验证** |
| `0x03` | 参数越界（动作码不在表内 / speed、repeat 非法） | fw.txt:361 第三项 | **推断** |
| `0x04` | 动作执行被中断（收到新命令） | — | **未定义，不得使用** |
| `0x05` | 底层驱动失败（舵机无响应） | — | **未定义，不得使用** |
| `0x06` | 资源忙（正在执行其他动作） | — | **未定义，不得使用** |
| `0x07` | TF 卡错误（文件系统/文件名不符） | fw.txt:440「拔掉 TF 卡，上报的错误码是 0x07」 | **已验证** |
| `0x08` | 帧超长（`LEN > 31`） | `frame.md` §3 的约定 | **本次提案** |

**三条硬规则：**

1. **`0x04`/`0x05`/`0x06` 现在是空的。** 固件在实现之前**不得**返回这三个值，后端也**不得**为它们写分支。
   留空比乱填好：一个错误码一旦上线并被前端翻译成中文，就再也改不掉了。
2. **未知错误码必须原样透传。** 后端收到表外的值，不得丢帧、不得归为 `0x03`，
   应写库并在 message 里显示 `未知设备错误 0x??` —— 这样将来固件加码时后端不需要同步上线。
3. **`0x05` 只能置 `rejected`。** 它不能置 `unknown`、不能置 `done`。
   收到 `0x05` 就意味着设备**明确拒绝**，这是全链路里最确定的一次否定。

### 2.1 `0x05` 与 `0x02` 的冲突

如果一条命令先收到 `0x81`（受理）再收到 `0x05`（错误），说明设备接了但执行中失败。
合法转移：`accepted → rejected`。这条转移在 `frame.md` §9.3 里已经列出。

反过来：`done` 之后再来同样的 `0x05`（例如 seq 回绕撞上），**必须丢弃**，不得改终态。

## 3. 传输错误（`transport` 列，不是错误码）

| 值 | 含义 | 命令记录 | 命令状态 |
|---|---|---|---|
| `ok` | 完整帧写入了串口驱动 | 建 | `pending` |
| `write_failed` | 确定一个字节都没写出去（端口未打开、`WriteFile` 立即失败） | **不建** | 无记录 |
| `partial_write` | 写了一部分，剩余失败 | 建 | **必须** `unknown` |

**为什么 `write_failed` 不建记录：**
一个从未存在过的命令不该出现在日志里。用户看到的应该是「刚才点了一下没反应」，
而不是「有一条 unknown 的命令」。前者是一次可重试的操作失误，后者会让人以为设备收到了。

**为什么 `partial_write` 必须 `unknown`：**
设备可能收到一个残缺帧并静默丢弃（校验和必然错），也可能因为少了校验字节一直等。
两种情况都无法证明「没执行」，所以只能是 `unknown`。

### 3.1 `transport` 与业务错误的区别（最容易混的一处）

| 情形 | `transport` | 业务 code | 有无命令记录 |
|---|---|---|---|
| 串口没打开 | `write_failed` | `50302`（串口未就绪） | 无 |
| 设备离线但串口正常 | `ok` | `0`（成功受理） | 有，最终可能 `unknown` |
| 动作码不在 21 个之内 | — | `40002` | 无 |
| 设备明确拒绝 | `ok` | `0` | 有，`rejected` + `error_code` |

**注意第 2 行和第 4 行**：业务 code 都是 0，但结果完全不同。
这就是为什么前端**不能**用 HTTP 结果判成败——只能看 `command` 事件里的 `status`。

> `50302` 是新码（`50301` 已被「设备不在线」占用）。
> 区别：`50301` = 链路可疑但会尝试，`50302` = 后端自己没准备好，**必然失败**。

## 4. 前端展示规则

| 后端状态 | 前端文案 | 是否可重试 |
|---|---|---|
| `pending` | 「已发送」+ 转圈 | 否（等） |
| `accepted` | 「设备已受理」 | 否（等） |
| `done` | 「已完成」+ 耗时 | — |
| `rejected` | 「设备拒绝：」+ 错误码翻译 | 是（换参数） |
| `unknown` | 「结果不明，请检查设备」 | 是（但会重复动作） |
| `superseded` | 「已被后续操作取代」 | — |
| `transport=write_failed` | 「未发出（串口不可用）」 | 是 |

**`unknown` 的文案不能写「失败」。** 它可能是成功但回执丢了。
写「失败」会让用户在设备其实已经做动作时再点一次，做两遍。

## 5. 与老文档的冲突（必须知道）

`be.txt:415-416`（后端计划第 6 周）写：

> 「机动：把这一轮的异常码统一成七条」
> 「代码里搜 raise，错误码都在 `0x01` 到 `0x07` 之间」

**这句话把两个域混了。** `0x01`~，`0x07` 是 `0x05` 帧里的**设备错误码**取值范围，
不是 HTTP 业务码。而且现有代码里已经有七个业务码（40001/40002/40100/40101/40400/50000/50301），
数量恰好也是七——很容易被误认为「已经做完了」。

**处理决定：**
- HTTP 业务码保持 `4xxxx`/`5xxxx` 五位十进制，**不动**（前端 `errors.ts` 已按此翻译）。
- 设备错误码保持 `0x01`~`0x08` 一字节十六进制，装进 `0x05` 的 `DATA[0]`。
- 两套编号**永不在同一个字段里出现**。命令记录里的 `error_code` 只存设备码。

## 6. 错误码该在哪里定义（唯一源）

| 域 | 唯一定义位置 | 谁生成 |
|---|---|---|
| 业务码 | `backend/app/errors.py` 的 `class BizError(IntEnum)` | 后端手写 |
| 设备码 | 本文件 §2 的表格 | 嵌入式手写，后端抄进 `backend/app/link/device_errors.py` |
| 传输值 | `backend/app/models.py` 的 `Transport` 枚举 | 后端手写 |

**禁止**在路由函数里内联数字（`return {"code": 40400}`）。一处漏改，前端就会遇到一个它不认识的码，
而 `errors.ts` 的兜底是显示「请求失败」——排查时完全看不出是哪一步。

## 7. 版本

- 新增业务码 = 次版本号 +1；前端 `errors.ts` 必须同步加翻译，否则用户看到的是原始 message。
- 新增设备码 = 次版本号 +1；后端**不需要**同步上线（§2 规则 2 要求透传），但应加翻译。
- 修改已有码的含义 = 主版本号 +1。这是最危险的一类改动：历史日志里的码会全部改变含义。
