## 0. 一句话原则

**WS 只推「已经发生的事实」，丢线之后靠 HTTP 重建，不靠补发。**

推论三条：

1. 事件是**事实通知**，不是**状态本身**。前端收到就覆盖对应字段，没收到的部分靠 `GET /api/devices/{id}/status` 补。
2. 断线期间丢掉的 `ack` **不会**补发。重连必须走 §6 的对账流程。
3. 后端不得因为「前端可能没收到」而重发事件——重发会让前端把同一个 `OK` 处理两次。

## 1. 建连与鉴权

### 1.1 为什么不能把 JWT 放 URL

浏览器的 `new WebSocket(url)` **不允许**自定义请求头，所以带不上 `Authorization: Bearer`。
把长期 JWT 塞进查询参数（`/ws/device?token=<JWT>`）的后果：

- URL 会进 Nginx/uvicorn 的 access log、反向代理日志、浏览器历史、抓包记录；
- 一个 24 小时有效的 token 一旦落进日志，等于长期凭证泄漏；
- 前端重连时 URL 不变，日志里会重复记录同一个 token。

> 现存代码 `frontend/src/utils/ws.ts:93-101` 就是这个写法，**必须改**，见 §7 D1。

### 1.2 一次性票据流程

```
① 前端  POST /api/events/ticket   （带 Authorization: Bearer <JWT>）
          body: { "device_id": 1 }
   ← 200  data: { "ticket": "<32 字节随机串>", "expires_in_sec": 30 }

② 前端  new WebSocket("/ws/device?device_id=1&ticket=<ticket>")

③ 后端  校验 ticket：存在 && 未过期（≤30s）&& 未使用过 && user_id 与 device_id 匹配
        通过 → 立即从票据池删除（一次性）
        不通过 → 以 4003 关闭，不升级连接
```

**票据规则：**

| 项 | 值 |
|---|---|
| 有效期 | 30 秒 |
| 使用次数 | 1 次（建连即焚） |
| 绑定 | `(user_id, device_id)`，不可跨用户、不可跨设备 |
| 存储 | 进程内存 `dict[ticket] -> (user_id, device_id, expire_at)` |
| 清理 | 每次签发时扫一遍过期项；进程重启即全部失效 |

> ⚠ 存内存意味着**必须单进程**。多 worker 时票据签发在 A 进程、建连落在 B 进程就会 4003。
> 这与 `frame.md` 要求串口唯一所有者是同一条约束的两种表现，不是两个问题。

### 1.3 关闭码

| code | 含义 | 前端该做什么 |
|---:|---|---|
| `1000` | 正常关闭（用户主动断开 / 页面卸载） | 不重连 |
| `4001` | 缺少或格式错误的参数 | 不重连，报错并检查代码 |
| `4003` | ticket 无效 / 过期 / 已使用 | **重新取 ticket 后重连**（不要复用旧 ticket） |
| `4009` | 同一用户对同一设备的连接数超限（上限 3） | 提示「该设备已在其他窗口打开」，退避 5s 后重连 |
| `1011` | 服务端内部错误 / 队列溢出 | 退避重连（1→2→4→8→10s 封顶） |

## 2. 消息格式

一律 **JSON 文本帧**（`ws.send(json.dumps(...))`）。二进制帧不使用，收到即忽略。

信封是**扁平**的，只有两个字段：

```json
{ "event": "state", "data": { } }
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `event` | string | 是 | 事件名，见 §3 |
| `data` | object | 是 | 事件负载；无负载时为 `{}`，**不要省略** |

> **没有** `event_id` / `ts` / `device_id` 三个信封字段，也不打算加。
> 理由：前端现有代码只读 `event` 和 `data`，多三个字段换不来任何能力——
> 事件去重靠「HTTP 对账 + 后端不重发」（§0 推论 3），不靠客户端判重；
> 连接本身就是按 `device_id` 建的，负载里再带一遍是冗余；
> 展示用的时间用客户端收到时刻就够，设备时间不可信。
> 少三个字段意味着少三处「后端填了、前端没读」的半成品。

## 3. 事件表

只有这 **5 种**，没有其它。

| `event` | 何时推 | 可丢 | 前端必须做什么 |
|---|---|---:|---|
| `state` | 收到 `0x03` 状态快照帧 | 是（可合并） | 覆盖电量/电压/动作/表情/音乐/天气字段 |
| `ack` | 收到 `0x81` 受理应答帧 | 否 | 结束该 seq 的等待态，标「已受理」或「失败」 |
| `link` | 设备 online 翻转，或串口打开/关闭 | 否 | 显示在线/离线 |
| `music` | 收到 `0x0B` 音乐状态帧 | 是（可合并） | 更新音乐 UI |
| `weather` | 服务端天气抓取结果变化 | 是（可合并） | 更新天气展示（与设备无关） |

**废除的四种事件及替代方案**（V1.0 草稿里有、v2.0 正式删除）：

| 废除 | 为什么删 | 用什么替代 |
|---|---|---|
| `snapshot` | 建连首帧要装「设备状态 + 未终结命令 + 场景进度」，字段随时间增长，最终长成一个分页接口 | 重连后主动调 `GET /api/devices/{id}/status` 与 `GET /api/commands/{id}`（§6） |
| `command` | 命令的六态生命周期（pending→accepted→done/rejected/unknown/superseded）在前端没有任何一个界面在展示，只有「按钮是否还在转」 | `ack` 事件 + `command_log` 四态（`/api/logs` 可查） |
| `scene` | 场景进度前端用 HTTP 响应里的 `steps` + 本地计时展示，后端逐步下发时每步都有 `ack` | `ack` 事件逐条到达即是进度 |
| `ping` | 五事件之外多一种心跳，前端要多一条分支，收益只是「更早发现死连接」 | 前端 75s 收不到任何消息就重连（§5.2），`state` 每 3s 一条，够用 |

> **事件名保留 `ack`**，不改叫 `command`。
> 改名收益为零（前端 `types/index.ts` 的 `WsEvent` 联合类型、`stores/pet.ts` 的 switch 都要跟着动），
> 而「`ack` 只表示 0x81 受理应答」这件事，靠 §4.2 的语义说明写清楚比改名字更有效。

## 4. 各事件负载

所有字段名 **snake_case**，与 HTTP 接口一致（全库统一，无例外）。

### 4.1 `state`

```json
{ "event": "state", "data": {
  "battery": 82, "voltage": 3.98, "action": 49, "face": 2,
  "music_state": 0, "track": 0, "weather_code": 3, "temp": 12
} }
```

- 来源是 `0x03` 帧，字段可能因 `LEN<9` 而缺；缺的字段**不出现在 JSON 里**（而不是给 0）。
- 8 个字段与 `GET /api/devices/{id}/status` 的 11 字段同源：status 多出
  `device_id` / `volume` / `updated_at` 三个「接口层才有的」字段。
- `voltage` 单位是**伏**（float，保留两位），不是毫伏——V1.0 草稿的 `voltageMv` 已废弃。
- `action` 是**设备当前执行的动作码**，不是「最后一次下发的动作」。用户点了按钮但设备还没动起来时，两者不同。
- 后端按帧到达即推，但**允许合并**（见 §5.2）。

### 4.2 `ack`

```json
{ "event": "ack", "data": { "cmd_id": "6f1f2c1e-8d1a-4c3b-9e77-0a1b2c3d4e5f",
                            "seq": 17, "status": "OK", "cost_ms": 312 } }
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `cmd_id` | string(uuid) | 否 | 对应 `POST /api/commands/send` 返回的 `cmd_id`。**后端能填就必须填** |
| `seq` | int | 是 | 串口序号 1-255，回传到 `0x81` 帧里的那个值 |
| `status` | string | 是 | 只有 `OK` / `ERROR` 两个值 |
| `cost_ms` | int | 是 | 从写串口帧到收到 `0x81` 的耗时，仅用于展示 |

**`ack` 是弱确认，它只说「这帧被设备受理了」。**

- `status` **没有 `TIMEOUT`**。设备没在 `T_ACK_MS`（600ms，见 `action-timing.md`）内回 `0x81`，
  是后端在 `command_log` 里记 `TIMEOUT`，**不推 `ack`**——没发生的事不推。
- 动作真正的完成（`0x02`）也不推事件，同样落 `command_log`。
  也就是说：**「按钮应该转多久」的唯一依据是 `command_log` 的 OK/TIMEOUT/ERROR，不是 `ack`。**
- 前端按钮的 3 秒变红是**纯展示的乐观反馈**，不写回任何命令状态，也不与 `T_ACK_MS` 互相引用。

> `cmd_id` 为什么是「可选」而不是「必填」：`0x81` 帧里只有 1 字节 seq，没有地方放 UUID。
> 后端靠 `seq → cmd_id` 的映射表补齐，正常情况下一定填得上；映射表已退役（超过 `SEQ_RETIRE_MS` 30s）
> 时才为空。前端遇到空 `cmd_id` 只能按 `seq` 认领，这是**退化路径**，不是主路径。

### 4.3 `link`

```json
{ "event": "link", "data": { "online": false, "reason": "device_silence", "since_ms": 9012 } }
```

| `reason` | 触发条件 |
|---|---|
| `device_silence` | 9 s（`DEVICE_SILENCE_MS`）未收到任何有效上行帧 |
| `port_closed` | 后端串口打开失败或被关闭 |
| `device_resumed` | 沉默后重新收到上行帧 |

> `online` 与「串口是否打开」「心跳是否在发」是三件独立的事，见 `frame.md` §8.2。
> 一个常见误判：串口开着、心跳在发，但设备一个字节都不回——这时设备是 offline 的。

### 4.4 `music`

```json
{ "event": "music", "data": { "state": 1, "track": 3, "volume": 18 } }
```

由 `0x0B` 触发，是**设备上报**。`state` 与 `DeviceStatus.music_state` 同义（0 停止 / 1 播放 / 2 暂停），
`track` 从 1 起，`volume` 0-30 可选。

**`music` 不是命令回执**：用户点了「播放」，命令成功与否看 `command_log`，音乐 UI 只能等这条事件变。

### 4.5 `weather`

```json
{ "event": "weather", "data": { "code": 3, "text": "阴", "temp": 12,
                                "updated_at": "2026-11-08T11:20:01+08:00" } }
```

由服务端抓取触发，与设备无关。字段与 `GET /api/weather` 的 `data` 完全一致（可选的
`location` / `source` 也允许出现）。

## 5. 顺序与合并

### 5.1 顺序

- 单条连接内，事件按 `hub.publish()` 的调用顺序 FIFO 发出。
- 后端可能有多个生产者（串口读循环、命令服务、天气抓取），它们都在同一个事件循环里 publish，
  所以顺序等于**事件循环的调度顺序**，不需要额外加锁。
- **不需要**跨连接保证顺序。

### 5.2 合并

| 事件 | 可合并 | 规则 |
|---|---:|---|
| `state` | 是 | 队列里已有未发出的 `state` 时，**用新的替换旧的那一条**，不追加 |
| `music` | 是 | 同上 |
| `weather` | 是 | 同上 |
| `ack` | **否** | 每条 `0x81` 都必须送达，否则前端会有一个按钮永远转 |
| `link` | **否** | 翻转是离散事实 |

> `state` 可以合并，是因为它是**幂等快照**：丢掉中间值不影响最终显示。
> `ack` 不能合并，是因为它按 `seq` 一对一认领，丢掉一条就等于丢掉一次配对。

**看门狗**：前端 75 秒内没收到**任何**消息就主动 `close()` 并走重连。
浏览器拿不到 WebSocket 的 ping/pong 控制帧，TCP 层的死连接（例如笔记本休眠后）在浏览器看来仍是
`OPEN`，`onclose` 永远不触发。设备 3 秒一条心跳、后端跟着推 `state`，75 秒的静默只可能是死连接。

## 6. 背压与丢弃

每个连接一个独立 `asyncio.Queue(maxsize=128)`（`WS_QUEUE_MAX`），由**独立的发送任务**消费，
业务代码只 `put_nowait`。

| 队列满时的行为 |
|---|
| `state` / `music` / `weather` → 丢弃最旧的一条，放入新的 |
| `ack` / `link` → **不允许丢**：立刻以 `1011` 关闭该连接，让前端重连并对账 |

**为什么用「关闭」而不是「阻塞」：**

如果在 `put` 上 `await`，一个慢客户端会拖住串口读循环——串口读循环一停，
设备发来的 `0x02` 就堆在驱动缓冲区里，最终溢出丢帧，所有命令都超时。
**一个浏览器的网速绝不能影响设备链路。**

## 7. 断线重连对账（必须实现）

```
① 取 ticket        POST /api/events/ticket  { device_id }
② 建连             ws://.../ws/device?device_id=..&ticket=..
③ 重建状态          GET /api/devices/{id}/status   → 覆盖 11 字段 + online
④ 补命令状态        对每个本地仍显示「等待中」的 cmd_id：
                    GET /api/commands/{id}（最多 20 条）
⑤ 恢复实时          此后只用事件，不轮询
```

**第 ③ 步不能省。** 没有 `snapshot` 事件，重连后本地状态是断线前的旧值；
不主动拉 status，界面会一直显示断网那一刻的电量和动作。

**第 ④ 步不能省。** 场景：用户点「打招呼」，WS 在 `ack` 之前断了，
那条命令的最终结果（`done` / `TIMEOUT`）在断线期间产生并丢失。
只有 `GET /api/commands/{id}` 能告诉前端「那条其实已经成功了」。

**第 ④ 步也不能无限做。** 只对「前端记录里状态仍非终态」的 `cmd_id` 调用，最多 20 条；
超过说明前端状态管理已经坏了，应该整页刷新而不是补 100 个请求。

**第 ④ 步之后仍缺的**：如果连 `cmd_id` 都没存下来（前端没升级），退化方案是
`GET /api/logs?device_id=1&size=20` 看最近 20 条 `command_log`，按 `action` + 时间对齐。
这条路只用来救场，不作为常规实现。

## 8. 与现有代码的差异清单（照此改，不要凭印象）

| # | 现状 | 契约要求 | 改哪里 | 代价 |
|---|---|---|---|---|
| D1 | `utils/ws.ts` 用 `/ws/device?token=<JWT>&device_id=` | 改为 `?device_id=&ticket=`，建连前先 `POST /api/events/ticket` | `ws.ts`（buildUrl + connect）+ 新增 `api/event.ts` | 中：多一次 HTTP 请求，重连逻辑要串起来 |
| D2 | `ack` 只有 `seq/status/cost_ms` | 增加可选 `cmd_id`，有就用于认领 | `types/index.ts` 的 `AckData`、`stores/pet.ts` 的 `onAck` | 小：约 5 行 |
| D3 | `stores/pet.ts` `TIMEOUT_MS=3000` 前端自判超时 | 计时器**改名 `DISPLAY_TIMEOUT_MS` 并降级为纯展示**：只把按钮标红、不改任何命令状态，文案用「结果不明」不说「失败」。命令结论只由后端 `command_log` 判定 | `stores/pet.ts` | 小：改语义不改时序 |
| D4 | pending 表按 `seq` 索引 | 有 `cmd_id` 时按 `cmd_id` 索引，`seq` 只在认领瞬间做一次映射 | `api/command.ts`（返回 cmd_id）、`stores/pet.ts` | 中：主键换了，所有查表点都要过一遍 |
| D5 | 无重连对账 | §7 五步（第 3 步拉 `status`、第 4 步逐条查 `commands/{id}`，上限 20 条） | `stores/pet.ts`、`utils/ws.ts` | 中：要用连接代次挡住旧请求的竞态 |
| D6 | 前端 75s 看门狗 | 无（五事件里没有 `ping`，靠 `state` 自然到达） | `utils/ws.ts` | 小 |

> **D3 和 D4 是同一个根因**：前端把「命令」当成「一次 HTTP 请求」来管。
> 契约里命令是一个**有生命周期的实体**，主键是 `cmd_id`，状态由后端单方判定。
> 这两条不改，联调时会出现「后端说超时、前端说成功」的对话，而这种 bug 极难复现。

> **seq 只活 30 秒。** `SEQ_RETIRE_MS` 之后 `seq → cmd_id` 的映射作废，前端若只拿 `seq` 当主键，
> 1-255 回绕后会把两条命令认成一条。这是 D4 必须改的硬理由，不是风格问题。

## 9. 版本

- 新增事件、新增字段 = 次版本号 +1，前端不认识的字段直接忽略。
- 删除事件、改字段语义、改 `cmd_id` 主键地位 = 主版本号 +1，两端同时上线。
- **禁止**用「前端忽略就行」来掩盖破坏性改动——前端忽略的是一个它本来就在用的字段时，
  它不会报错，只会显示错。
